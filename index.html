Context

How Hive fits in Hadoop

Hadoop is a stack of layers. Each layer does one job. Hive sits at the top — it gives you a way to ask questions in SQL.

Query Layer — Hive
You write SQL here. This is what you interact with.
Compute Layer — MapReduce / Tez
Takes the SQL, breaks it into parallel jobs.
Resource Layer — YARN
Decides which machines run which jobs.
Storage Layer — HDFS
Stores the actual files across many machines.

You use Hive (top). It uses everything underneath.

Architecture

Inside Hive: 4 pieces

When you type a query, it passes through four components. Let's follow the flow.

Step 1
Client
You, in Beeline or a JDBC app. You send SQL text.
Step 2
HiveServer2
The "door." Receives queries, manages sessions.
Step 3
Metastore
The "catalog." Knows the tables, columns, partitions.
Step 4
Execution Engine
Turns SQL into jobs (Tez / MapReduce) and runs them.
HDFS
Where the data actually lives. The engine reads it.
Result
Comes back to you as a table.

Client sends SQL → HiveServer routes it → Metastore gives structure → Engine runs it on HDFS.

Partitioning

What is a Partition?

Splitting a table into sub-folders by column value.

orders_partitioned/
├── city=Tunis/
├── city=Sfax/
├── city=Sousse/
└── city=Ariana/
Faster queries: only read the needed folder
Bucketing

What is Bucketing?

Splitting data into a fixed number of files by a hash of a column.

Mainly used to speed up JOINs and sampling.

CREATE TABLE orders_bucketed (
order_id INT,
customer STRING
)
CLUSTERED BY (order_id) INTO 4 BUCKETS;
Partition = folder tree
Bucket = hashed file inside
Caveats

Limitations of Hive

Not for real-time queries
No fast row-level updates
Not for OLTP workloads
High latency per query

Hive is built for throughput, not for latency.

Use case

E-commerce pipeline

Imagine a Tunisian online shop. Every click and order has to be saved fast and later analyzed deeply. Two different jobs, two different tools.

1. Capture
Each order is written to MongoDB instantly — as JSON, no schema required.
2. Dump
Every night, raw orders are copied to HDFS — cheap, safe, permanent.
3. Structure
Hive reads the raw files, organizes them as tables, partitioned by city.
4. Analyze
Analysts run SQL in Hive to produce dashboards and reports.
NoSQL = fast capture
Handles the live traffic. Writes are instant. Schema is flexible.
Hive = deep analysis
Handles the heavy queries. Reads terabytes. Produces reports.

Two jobs, two tools. NoSQL catches the data. Hive understands it.

Behind the scenes

What happens when you type SQL

1. Parse
SQL becomes an abstract syntax tree
2. Plan
Build a logical plan, optimize it
3. Compile
Translate to Tez / MapReduce DAG
4. Execute
YARN runs tasks across the cluster
// You see this in the logs when a query runs
Status: Running (Executing on YARN cluster with App id application_...)
Map 1 ...... container SUCCEEDED 1 1
Reducer 2 ... container SUCCEEDED 1 1
DAG finished successfully in 0.80 seconds

Your SQL is not executed. It is translated, then distributed.
